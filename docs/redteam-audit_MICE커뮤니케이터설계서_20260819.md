## 축별 상세

### 축 1 · 내용 검증

**[C-1] 🔴 코멘트 노출 범위 미정의 — 권한 위생 자기모순**
- **위치**: §4 comments DDL / §10 S7 화면 명세
- **원문**: comments는 "내부·발주처 공용 스레드", S7은 "대기 항목 리스트 → 미리보기 → 승인/수정요청"
- **문제**: 코멘트가 deliverable 단위 단일 스레드인데 가시성 필드가 없다. S7이 코멘트를 함께 렌더하는 순간, "이 발주처 요구가 과하다" 류의 내부 대화가 발주처에게 그대로 보인다. §6.3의 "내부 초안·단가·정산은 구조적으로 노출 불가" 주장과 스키마가 모순.
- **근거**: 스키마 대조 — visibility 부재는 원문에서 직접 확인.
- **권고**: `visibility enum('internal','shared')` 추가(기본 internal), 발주처 화이트리스트 쿼리는 shared만. 발주처가 작성한 코멘트는 shared 강제.

**[C-2] 🔴 프론트-서버 강결합 — "서버 후행 이식" 확정 요구와 충돌**
- **위치**: §2 아키텍처, CLAUDE.md §3 레포 구조(`lib/ supabase client`)·§4 Phase(DB→Drive→UI 순)
- **문제**: 프론트가 Supabase client를 직접 호출하는 전제라 서버 없이는 화면 한 장도 못 만든다. 후행 이식 시 전 화면의 데이터 접근 코드를 재작업하게 된다.
- **근거**: Phase 1(DB)·2(Drive)가 UI(Phase 3)의 선행 필수로 명기됨.
- **권고**: DataProvider 어댑터 계층 신설 — 프론트는 인터페이스만 호출, MockProvider(픽스처) 선행 → SupabaseProvider·Drive 계층 후행 교체. 인터페이스는 §4 스키마와 1:1로 동결.

**[M-1] 🟡 OAuth 운영 조건 누락 — 7일마다 죽는 서버**
- **위치**: §2 "Drive 인증 (확정)"
- **문제**: "최초 1회 동의 → refresh token 저장"으로 끝. Google OAuth 동의 화면이 External+**Testing** 상태면 refresh token이 **7일 후 만료**되어 매주 재인증 장애가 난다. Drive 전체 scope는 restricted scope라 Production 전환 시 검증 이슈도 있다(단, 100인 미만 개인용은 '미확인 앱' 경고 통과로 사용 가능).
- **근거**: 웹 검증 2026-08-19 — <cite index="3-1">External 사용자 유형 + Testing 게시 상태 프로젝트의 refresh token은 7일 만료</cite>, <cite index="2-1">해결은 게시 상태를 In production으로 전환하는 것</cite>, <cite index="13-1">100인 미만 개인용 앱은 검증 없이 '미확인 앱' 경고를 통과해 계속 사용 가능</cite>.
- **권고**: 개인 계정이 아닌 **전용 운영 Google 계정** 분리 + OAuth 앱 **Production 게시**를 설계서에 절차로 명기. PM 개인 계정 사용 시 refresh token 유출 = 개인 Drive 전체 노출 리스크도 함께 제거된다.

**[M-2] 🟡 프록시가 대용량 디자인 원본에서 죽는다**
- **위치**: §7.4
- **문제**: 키비주얼·제작물 원본(AI·PSD·영상)은 수백 MB가 일상이다. Edge Function 프록시는 이를 감당하지 못한다.
- **근거**: 웹 검증 2026-08-19 — <cite index="32-1">Edge Function 메모리 한도는 150MB(heap)+150MB(external)이며, 50MB 미만 스토리지 객체 다운로드에서도 메모리 초과 보고가 있다</cite>, <cite index="25-1">wall clock 한도 400초</cite>, <cite index="30-1">응답 전 idle 150초 초과 시 504</cite>.
- **권고**: ① 컨펌 발송 조건에 "미리보기 포맷(PDF·PNG·JPG) 버전 필수" — MICE 실무 관행(시안은 PDF/JPG로 컨펌)과도 일치 ② 프록시는 ReadableStream 패스스루 + 사이즈 캡 ③ 내부 멤버는 행사 루트 폴더 팀 공유로 Drive 직접 접근 병행.

**[M-3] 🟡 중복 방지 선언-스키마 불일치** — §11 "email 기준 upsert" vs DDL에 unique 없음. 동시·재임포트 시 중복 행 확정. → `(project_id, lower(email))` partial unique index 2건(rsvp_contacts·attendees).

**[M-4] 🟡 final 전이 비원자성** — §5·§7.5에서 copy 실패 시나리오 미정의. 승인은 됐는데 06 폴더에 확정본이 없는 상태 발생. → 스냅숏 성공 후에만 final 커밋, 실패 시 approved 유지 + 재시도 큐.

**[M-5] 🟡 인박스 스캔 취약 + 자동 rename 부작용** — modifiedTime 증분 폴링은 이동·페이지 경계 유실에 약함(Drive Changes API가 정석). "원클릭 연결 시 규약화 rename"은 타인이 직접 올린 파일명을 앱이 임의 변경 — 협업자 혼란, 파일명 기반 외부 참조 파손. → Changes API(startPageToken) 채택, rename은 기본 off 옵션.

**[M-6] 🟡 토큰 URL 유출 관리 부재** — 이메일 포워딩 한 번이면 제3자가 컨펌 권한을 얻는 구조인데 기본 만료·referrer·로그 정책이 없다. → 기본 만료(행사일+30일), `Referrer-Policy: no-referrer`, 서버 로그 토큰 마스킹.

## Steelman 반대 시나리오

**가장 강한 반론**: "서버 후행 + 어댑터 계층은 이중 작업이다. Supabase는 로컬 CLI로 즉시 띄울 수 있으므로 처음부터 실DB로 가는 것이 Mock 픽스처 작성·유지비보다 싸다."

**원 결론의 방어 평가**: 부분 타당하다 — Supabase 자체는 후행시킬 이유가 약하다. 그러나 이 프로젝트의 최대 리스크는 DB가 아니라 **Drive OAuth·프록시 계층**(M-1·M-2가 증명)이며, 이를 후행시켜 UI/UX 검증과 발주처 데모를 먼저 확보하는 이점이 픽스처 유지비를 상회한다. 단 조건이 있다: **DataProvider 인터페이스를 §4 스키마와 1:1로 동결**하지 않으면 이식 시 재작업이 어댑터의 이점을 잠식한다. 조건부로 사용자 결정을 지지한다.

## 대안 · 보완 권고

1. **더 나은 접근**: 어댑터 3분할(MockProvider → SupabaseProvider → DriveFileStore)로 이식을 2단계로 쪼개면, Supabase 이식 후에도 Drive 없이 앱이 동작(파일만 mock)해 리스크가 직렬화된다.
2. **사각지대 보완**: 발주처 데모 라우트(`/c/demo`)를 Mock 단계 산출물로 명시 — 프론트 완성 시점에 발주처·내부 이해관계자 시연이 가능해진다.
3. **조건부 권고**: v1.0 결론은 [C-1·C-2 수정 + M 전량 반영 + 인터페이스 동결] 조건 하에서 유효. 미충족 시 프론트 우선 전략 자체를 재검토해야 한다.
